# 怪物动作速度与放刀时机（SPEED）

> 状态：设计结论，**审查后修订版**，2026-10-11。研究阶段只读，没有改代码；本文是拟定 v1.6 的依据。
>
> 本版相对上一版的主要变化（三路审查共 23 条意见，逐条处理见第 9 节）：
> - **C 不再在消息钩子里读**。离线验证用的 C 全部来自消息之后下一帧的帧回调，钩子那一刻从来没采过；而 CoreState 恰好在发消息的那一帧按招切换。v1.6 改为从登记后的第一个帧回调起读。
> - **触发量改为 E5**：逐帧积分 CoreState，用 hs 自己的递减当时钟，C < 1 时按 1 处理。C 不变时，E5 与上一版的 E1 逐位相同，所以上一版的回放数字对它照样成立。
> - **L=25 不再称「冻结、已验证」**。它是在 em27 / 2c 上定出来的样本内值。L=25 和 L=28 之间的取舍交给用户，和「打断（INTERRUPTED）算不算空放」一起定。
> - **验证方案重写**。上一版的 A 阶段判据在计划样本量下，对已知的 em20、em23、em27 也有 17~41% 的误判失败率；B 阶段只验 2 只怪。现在改为：A 阶段合并判定、逐只报告；B 阶段以怪为抽样单位；上线后再加被动监控。
>
> 数据：4 段，按 session 号筛选。r1 = 1791644664（rc 标定，L 在 20~36 轮换）、2a = 1791658621（v1.5，L=26）、2b = 1791662423（v1.5，L=26→30）、2c = 1791687210（v1.5.1，L=30，快照时还在进行）。怪：em19 = Em0152、em20 = Em0153、em23 = Em0156、em27 = Em0160，另有 em18 = Em0151 少量。
>
> 记号：帧 = 1/60 s，s = 秒。hs、he = `HitStartRemainFrame`、`HitEndRemainFrame`；A = 登记后第一次读到的 hs（名义帧）；C = 怪物的 `get_MotionSpeed_CoreState()`；m = max(1, C)；c_first = 以进入 (2,23) 为 0 的首个接触时刻；W0 = 0.328 s，W1 ≥ 0.944 s；g = 首个接触 − 攻击判定激活。
>
> 出处标注：**实测** = 数据直接算出（带样本量）；**推测** = 由类型库或机制推断，没有直接测到。数字后的标注：（复算）= 上一版综合时用独立脚本重算过；（审查复算）= 本轮修订时用 `speed_research/revise/` 下的脚本独立重算过；（A）（C）（I）分别来自激活时刻、接触回放、游戏内部结构三路研究。区间如无说明，都是 Clopper–Pearson 双侧 90%。

## 0. 一页结论

1. **问题**（实测）：hs 的初值是怪物在 1 倍速下的名义帧，之后在接收端按真实时间每秒减 60；怪物却按 CoreState 倍速推进动作。所以 C > 1 时，攻击比倒数早到约 `A·(1 − 1/C)/60` 秒。v1.5.1 把 hs/60 当真实剩余时间。2c 的 em27 C 在 1.08~1.264 之间，有接触的 6 刀里 5 刀放早，首个接触比 R0/60 早 0.207 s（中位，n=6）。

2. **机制结论成立，可以外推**（4 只怪实测一致）：
   - 倒数 = 名义帧初值 + 接收端的真实时间计时器；
   - 怪物按 CoreState 倍速走。CoreState 含按招的怒时倍率，数据显示它在进入动作的那一帧变（2.1 l），所以接替动作时也会变。
   这些都是所有怪共用的管线（`AttackAreaResult` / `EnemyCharacter.cMotionSpeed`），不含按怪的参数。

3. **v1.6 规则**（修订后；没有任何按怪、按招的参数）：
   ```
   m_k = max(1, C_k)                         C_k：第 k 次帧回调读到的发送者 CoreState
   X  += (hs_{k−1} − hs_k) · (m_{k−1} − 1)   从登记后第一个帧回调起累加，用 hs 自己的递减当时钟
   Q   = (hs − X) / m_k                       真实剩余帧；C 不变时等于 hs − A·(1 − 1/m)
   ```
   - 最早一段 DANGER 候选满足 `22 ≤ Q ≤ L` 时请求 (2,23)。
   - 候选的筛选和取最小值都按 Q；否决仍按原始 hs。
   - 读不到 C 的结果不放刀，但照样参与否决。

4. **L 没有定死**。现有数据只能给出两个候选（详见 3.4、3.5 节）：

   | | L = 25（默认） | L = 28 |
   |---|---|---|
   | 已知怪的放早（两套回放，样本内） | 2/90、3/92 | 0/90、1/92 |
   | em27 型怪的放早 | 样本内 4~6%，按留一只怪约 13% | 样本内 0~2%，g=0 上界 9% |
   | 空放，打断计入 | 约 24~26%，正好卡在 25% 门槛上 | 约 30~32%，多半不过门槛 |
   | 空放，打断不计入 | 约 2%（63 刀里只有 1 次纯空挥，按 L 分不出差别） | 同左 |

   用户要先定「打断算不算空放」：
   - 算（看重原生抵消动画）→ 用 25；
   - 不算（看重不挨打）→ 用 28。

5. **对新怪的预期**，按怪型分开看，合并成一个数没有意义：
   - **左尾轻**的怪（像 em19、em20、em23）：这 3 只怪在接触层 E1@25 回放里合计放早 0/43（90% 上界约 7%），有接触接住约 90~95%。
   - **左尾重**的怪（像 em27）：L=25 时放早约 4~13%（样本内 4~6%，按留一只怪约 13%），有接触接住约 83~91%。
   - **左尾比 em27 还重**的怪：现有数据回答不了。em27 在 g=0（攻击一激活就碰到人）时，L=25 的早到上界约 24%。

6. **结论降级**。上一版「参数已冻结，可直接验收」撤回，现在的状态是：
   - 机制成立，规则形式可以进入实现；
   - L 是样本内定的默认值；
   - 验收前先跑一轮只记录、不放刀的 A 阶段（仓库里现成的 ATP + APCal 探针），在至少 4 只新怪上做机制检验（其中 1 只是历战个体）；
   - 然后以怪为单位验收（B 阶段）；
   - 上线后用 FIRE 记录做被动监控（C 阶段）。
   合计 4~5 只新怪，约 2 小时游戏时间。之后正常打猎就是持续验证，不需要每只怪专门去测。

7. **要用户拍板的两件事**：
   - 打断计不计入空放（它决定 L 取 25 还是 28）；
   - 空放门槛对 L=25 来说正好在预测值上，B 阶段的通过概率只有五六成，加样本也改变不了（第 7.2 节）。

### 2.2 推测（类型库 + 数据，没有直接测到）

- **发送端**：
  - 怪物进入动作时，`app.mcEnemyAttackAreaDetector`（活体读到 `_SendTiming = IMMEDIATE`）按动作 GUID 和目标方位 DIR4，从 `app.user_data.AttackAreaParam` 取出 `AttackAreaData`；
  - `DetectedData.initData` 把 `AttackStartFrame` / `AttackEndFrame` 写进 hs、he，再用 `cMsgEmAttackAreaResult` 发出（（I））；
  - 按招的 CoreState 倍率也在进入动作时设定，和发消息在同一帧，谁先谁后类型库判断不了（2.1 l）。
- **接收端**：主角身上的 `mcHunterAttackAreaResultHolder` 每帧调用 `AttackAreaResult.update()` → `DetectedData.update(Single, Capsule)`，按全局 dt 递减。它拿不到怪物的速度倍率，也不知道怪物的顿帧。
- **烘焙表**按平静状态、默认速度生成：
  - 动作设计里自带的变速（Sequence、BlendTree、MoveAction……，即上面的 h）已经算在里面；
  - 运行时的状态倍率 CoreState（怒、疲劳、按招的怒时倍率）不在里面。
- **随机变速轨道**（本轮用 MCP 只读 get_type 核对过类型，没测过行为）：
  - `app.motion_track.EnemyVisual.cRandomSpeed` 有 `_Min / _Max / _EnterInterFrame / _ExitInterFrame / _IsContinuousSpeed`；
  - `app.mcEnemyRandomMotionSpeedUpdator` 有 `enter / exit(cRandomSpeed)`、`_EaseRandomMotionSpeed`、`_TargetRandomMotionSpeed`。
  推测它在动作片段里随机取一个速度，缓入缓出地写进 Random 分量。用到这类轨道的怪，有效速度会在倒数中途变化，烘焙表也不可能含一个随机值。现有数据里 Random 恒为 1，没见过。
- **CoreState** 在进入动作时随怒 / 疲劳状态和招式设定。对象存活期间如果接替到下一个动作，它会跟着变（2.1 n）。上一版写的「存活期间很少变」只对单个动作内成立。

### 2.3 生成模型（由 2.1 推出）

```
hs(t)    = A − 60·τ(t)                         接收端计时器；τ = 游戏时间（单帧上限约 0.133 s）
P(t)     = ∫ 60·m(τ) dτ                        怪物走过的名义帧；m = CoreState（2.1 n：会随接替动作变）
激活时刻 ≈ P(t) 走完 A 的那一刻 + b             b ≈ −0.022 s（约 −1.3 帧，全局常数）
Q(t)     = (A − P(t)) / m_now = (hs − X) / m_now，X = Σ Δhs·(m − 1)       真实剩余帧
首个接触 = 激活 + g                             g ≥ 0，由招式几何和站位决定
```

m 恒定时 Q = hs − A·(1 − 1/m)，就是上一版的 E1。全局偏移 b 的三种估法：（A）−0.014~−0.020 s，（C）−0.023 s，（I）2.0 名义帧再加 0.27；复算按留一只怪取得 −0.020~−0.025 s。几种口径等价，规则里不显式使用，直接吸收进 L。

### 2.4 修正后仍剩的左尾（实测；原因部分是推测）

修正后激活残差（E1，不减 b）< −0.10 s 的有 49/311 个单位，**全部来自 em27**。其中有重复计数：同一次物理激活常常被前后两个结果对象各预告一次，49 个单位只对应约 34~38 次物理激活（去重口径不同，审查复算 34，审查 mechanism 38）。

按成因分：
- **接替链里的中途加速**：(0,131) 第 2、3 段（A≈324 / 345）与后继 (0,132) 的前两段是同一次激活。(0,131) 的 8 个单位全部在倒数中途加速了约 5%（1.025→1.076 或 1.080→1.134）。E1 早 0.13~0.19 s，E5 现实界早 0.07~0.11 s（2.1 n）。上一版说「C=1.025 和 1.080 时差不多，所以不像速度估错」，这个推理不成立：两种情形的增幅都是约 5%，差不多正是中途变速的预测。
- **后继结果重新登记**（审查 mechanism，本轮没有独立重算）：(0,107) 预告的激活早 0.21~0.27 s，但后继 (0,108) 在激活前 0.44~0.55 s 登记，它自己的残差只有约 −0.03。规则对所有活着的结果取最早的 Q，所以实际放刀由后继决定。现有数据上真正起保护作用的是这个，不是 L 的余量。它对新怪成不成立，取决于后继消息来得够不够早。同一审查还发现，(0,107)→(0,108) 的有效速度比登记时的 C 快 1.14~1.20 倍，后继动作里有一个不在 CoreState 里的隐藏因子（h≈1.3），E5 也修不掉。
- **(0,79) 的 A≈212 变体**：没观察到中途变速的单位也早 0.17~0.24 s（多数在倒数期间没有采样，C 变没变不知道），原因不明。同一招 A≈184 的普通版残差约为 0。另有 1 个 (0,79) 单位在倒数中途从 1.025 变成 1.199，E1 早 0.49 s。
- **短招** (0,76)、(0,75)：早 0.11~0.15 s，C=1.134；(0,85) 一例早 0.55 s。原因不明。
- 反方向的有 em23 (0,113)，约 +0.3 s。

左尾和修正量强相关（审查复算，E1 − b < −0.10 s 的比例，按修正量 A(1−1/C)/60 分箱）：

| 修正量 | 比例 | 构成 |
|---|---|---|
| < 0.05 s | 1/64 = 2% | 5 只怪都有 |
| 0.05~0.15 s | 13/132 = 10% | em19、em20、em23、em27 都有 |
| 0.15~0.30 s | 5/57 = 9% | 45 个来自 em27 |
| ≥ 0.30 s | 17/46 = 37% | 43 个来自 em27 |

A ≥ 150 帧的 67 个单位里，66 个来自 em27；其余 3 只怪 A < 150 的 101 个单位左尾为 0，em27 A < 150 的为 9%。也就是说，「长预告 × 高 C」这一块只有 em27 一只怪的证据，而且整体偏早。新怪如果长预告多、C 又比 1.264 还高，就是在已知不利的方向上外推。

### 3.4 L 的选法：哪些是样本内、哪些是样本外

**上一版预注册的选法**：取训练集上「早到率 ≤ 5%」的最小整数 L，在全部数据上得到 25。审查指出了三点，复算都成立：

1. **(C) 的回放不满足这个选法**。L=25、26 时 em27 都是 3/47 = 6.4%，超过 5%；要到 L=28（1/47）才满足。上一版把「复算 2/47，(C) 3/47」都当作满足，是错的。复算在 L=27 时已经 0/90；(C) 没有算 27，到 28 才满足。所以两套回放同时满足的是 27~28。
2. **L=25 实际上是 2c / em27 定出来的**（审查复算）：
   - E1@24 的 6 个早到全是 em27：(0,82) ×2、(0,76) ×2、(0,75)、(0,79)，其中 5 个来自 2c；
   - L 从 24 到 25 消掉的 4 个里 3 个来自 2c；L=25 剩下的 2 个（2c 的 (0,76)、(0,75)，C=1.134）也来自 2c；
   - 去掉 (0,82)（5 个单位）或 (0,76)（4 个单位）中的任何一招，选出的 L 就从 25 变成 23；去掉 em27 其余任何一招都不变；
   - 其余 3 只怪在 L=23~45 全部 0 次早到，对 L 没有提供信息。
3. **真正的留出结果**（审查复算）：
   - 只用 2c 之前的 r1/2a/2b 选 L，会选到 23（训练集早 1/64）。这时 2c 是真留出：窗口内 21/26，早 5/26 = 19%（区间 8~36%）。
   - 留一只怪时，留出 em27 那一折选到 23：em27 早 6/47 = 12.8%（5.7~23.6%）；合并留出早 6/90 = 6.7%（2.9~12.7%）。

**g=0 上界**（审查复算，激活层，按物理激活去重）：L=25 时放刀后预测激活约在 (25 − 0.46)/60 = 0.409 s。如果攻击一激活就碰到人（g=0），激活残差 < −0.081 s 就算早到。各怪满足这个条件的比例：

接触层 em27 只早 2/47，差距来自 g（中位 +0.02~+0.05 s）。对 g 小的新怪，同样的残差分布会早到得多。所以 L=25 的早侧余量很薄：只比典型激活时刻多出约 0.06 s（约一个 IQR），其余靠 g。

- 上一版用「r1 在 L ≤ 24 时空放 0/14」支持 L=25，口径是 hs。换成 Q 以后，r1 的 L=20/24 档大多在 Q < 22 处放刀，E1@25 根本不会在那里放。E1@25 的触发区间 Q∈[22,25] 里只有 9 刀，空放 1 次。方向没变，但证据只有每档 9 刀。

- logistic 均值约 24%；
- （C）按怪等权、留一只怪拟合空放模型再 bootstrap：26.1%，90% 区间 13.9~37.1%，怪间 16~33%。

### 3.7 C 的读取时刻（审查新增）

实测（审查复算）：
- 离线验证用的 C 全部来自消息之后的下一个帧回调（2.1 m）；
- CoreState 恰在发消息的那一帧按招切换（2.1 l）；
- 上一版的伪代码却在 `receiveGameMessage` 钩子里同步读。钩子在帧中间，读到的可能是上一个动作的值。

影响（悲观情景）：用「消息前最近一条 EMINFO 的 C」代表钩子可能读到的旧值。有消息前样本的 308 个激活单位里，123 个与首帧值不同（不过这条样本多数在消息前 2.9 s 左右，代表的是上界）。接触层：

| 情景 | E1@25 放早 | 其中 em27 | E1@28 放早 |
|---|---|---|---|
| 首帧 C（验证口径） | 2/90 | 2/47 | 0/90 |
| 消息前 C | 9/89 = 10.1% | 8/46 | 8/89 |

激活层上，这 123 个单位的 E1 残差中位从 −0.026 变为 −0.082，Q10 从 −0.180 变为 −0.411。加大 L 救不回来。

所以 v1.6 不在钩子里读 C，从登记后的第一个帧回调起读，这正是离线验证的采样点。第一次放刀判断本来就不可能早于这一帧（求值在帧回调里），所以不会引入延迟。钩子时刻的值是否与首帧一致，A 阶段由 ATP 的 INIT 快照回答，只作报告。

## 4. 普适性论证

### 4.1 机制性的部分（对没见过的怪也成立）

- **倒数的语义**：接收端计时器（2.1 d、e）和名义帧初值（2.1 b、c）是主角身上的 `AttackAreaResult` / `DetectedData` 的行为，与怪是哪一只无关。5 只怪表现完全一样：初值偏差的中位都在 −0.18~−0.29 帧，计时速率都是 1.000。
- **速度倍率的位置**：CoreState 是 `app.EnemyCharacter.cMotionSpeed` 的一个分量，是所有怪共用的基类字段，读取方法 `get_MotionSpeed_CoreState()` 对每只怪都一样（4 段 JSON 里 2805 条 EMINFO 全部读到数值，复算）。数据显示它在进入动作的那一帧变（2.1 l），所以逐帧读、逐帧积分（E5）对接替动作和怒 / 疲劳切换都成立；只在登记时读一次（E1）就做不到。
- **修正公式没有拟合参数**：`Q = (hs − X)/m` 直接由「表按 1 倍速、怪按 m 倍速、计时器按游戏时间」推出。
  - 修正量小（< 0.15 s）时，各怪的斜率都与 1 相容；
  - 修正量大时，只有 em27 的证据，而且斜率 1.10（1.05~1.26），偏修正不足（2.1 f、2.4）。
- **抵消窗口**是主角侧的：W0 = 0.328 s、δ ≈ 0，4 只怪的接住都与它一致（38/40）。
- **早侧失败的结构**（上一版这里说过头了，已更正）：放早 ⇔ 激活残差 + g < W0 − (L − d̄)/60。前一项是机制量，可以外推；g 是按招、按站位的几何量，不能外推。g 小的怪，同样的残差分布会早到得多（3.4 节 g=0 上界）。

### 4.2 拟合出来的部分（外推有风险）

| 量 | 值 | 怎么来的 | 外推风险 |
|---|---|---|---|
| L | 默认 25（Q 单位），备选 28 | 25 由 em27 的两招和 2c 定出（3.4 节），样本内 | em27 型新怪放早约 4~13%；左尾更重或 g 更小的怪更高 |
| L_min | 22（Q 单位） | 沿用 v1.5.1。按 Q 计取 18~22 结果相同（（C）） | 低 |
| b（不进规则） | −0.022 s | 3 路 + 复算，留一只怪稳定在 −0.020~−0.025 | 帧率依赖未知（数据覆盖 50~117 fps） |
| C < 1 按 1 | 规则 | 保守选择，不是拟合 | 疲劳时放刀偏早，空放会多一点 |
| C 合法范围 | [0.5, 2.0] | 只用来剔除坏值；验证覆盖 0.922~1.264 | 超出 0.92~1.27 的放刀属于外推，单独报告 |
| 空放 | 约 24~26%，上界约 37% | 统计模型 | **不能外推**：取决于怪会不会被上捞斩打断 |

### 4.3 现有数据覆盖不到的

- **其他速度分量**：Random、Action、Replica、WaitPacket、WaitPacketReserved 在全部数据里恒为 1。类型库里确有动作中途随机变速的轨道（2.2 节）。新怪如果用到它，又没有算进烘焙表，规则会按 `A·(1 − 1/Random)` 的量级出错；补救是 m 改为 CoreState × Random，而且必须逐帧读（E5），只读一次不够。
- **长预告 × 高 C**：只有 em27 一只怪，而且偏早（2.4 节）。新怪 C 超过 1.264 或长预告很多时，是在不利方向上外推。
- **左尾的保护机制**：现有数据上起作用的是后继结果重新登记（2.4 节）。新怪的后继消息来得够不够早，不知道。
- **攻击几何 g**：只在 4 只怪上测过。
- **ATK 配对的盲区**：按 a5 = reqset 配对会整招丢失（1.2 节），新怪上也会这样，激活层验证就成了按招筛过的子集。
- **不可防御攻击**：候选 DANGER 条目里有 73 条 guard = UNABLE_GUARD，全部来自 em27 的 (0,79)、(0,80)、(0,131)、(0,132)；63 次真放刀里没有一次触发在这类条目上（审查复算）。它们能不能被抵消，从来没测过；新怪的大招常是这一类。
- **C < 1**（疲劳）只有 12 个激活单位，**历战 / 历战王**（`EmParamLegendary.MotionSpeedRate` 从哪个分量进来）没测过。
- **联机**：副本不放刀（v1.5 的闸门），主机端没测过。
- **帧率**：放刀发生在 Q 第一次 ≤ L 的那一帧，读数平均比 L 低半个帧步长。30 fps 比 70 fps 晚约 0.5 帧（0.008 s），但没有低帧率数据；单帧超过约 0.133 s 时计时器被钳制（2.1 d）。

### 4.4 结论

能外推的是**公式和它依据的机制**：名义帧初值、接收端计时器、按 CoreState 逐帧推进。不能外推的有三样：**L 的余量够不够**（取决于新怪的左尾和攻击几何）、**修正量很大时的精度**、**空放率**。

各自怎么检验：
- 机制要在新怪上做一次检验。不放刀也能做，因为 ATK 与站位无关（A 阶段）。
- L 的余量和大修正量的精度，A 阶段能测出风险（左尾、g、后继提前量），但结论要靠验收和上线后的监控。
- 空放只能靠验收。

验收通过也只能说明测过的那几只怪。普适性要靠「机制检验通过」和「持续监控没有发现成片的放早」两条一起支撑。

## 5. 推荐规则（v1.6 拟定，审查后修订）

本版只改**触发量的时间基准**这一个变量（E5c，以及与之绑定的候选筛选、取最小值）。否决、过滤、streak、副本闸门、抓取否决都与 v1.5.1 相同。

### 5.1 公式与参数

| 项 | v1.5.1 | v1.6 |
|---|---|---|
| 触发量 | Q = hs | **Q = (hs − (X − X0_e)) / m**；m = max(1, C) 逐帧读；X 从登记后第一个帧回调起按 hs 的递减累加；X0_e = 条目首见时的 X |
| 区间 | 22 ≤ hs ≤ 30 | **22 ≤ Q ≤ L**，L 默认 25（用户确认；备选 28） |
| 候选筛选、取最小值 | 按 hs | **按 Q**（候选不再受原始 hs ≤ 90 的外层门限制） |
| C 的读取 | — | **登记后第一个帧回调起，每帧一次**：`EnemyManager:findEnemy_SystemIndex(idx):get_Character():get_MotionSpeed_CoreState()`，同一帧按 idx 缓存；不在钩子里读，不跨帧持有怪物对象 |
| 读不到 C | — | 首帧读不到：这个结果**不放刀**（照样参与否决），计 `speedfail`；中途读不到：沿用上一帧的 m，计 `speedhold` |
| 否决 | hs ≤ 90 的长窗口 / 抓取 | **不变**（W_long 60、H_veto 90 仍按原始 hs/he）；另计 `vetoq` |

### 5.2 伪代码（只示意改动点）

```lua
-- on_message（新结果登记）：钩子里不读速度，只记怪物编号（拼 em 字符串时本来就读了）
tr.idx = r:call("get_EmSystemIndex")
tr.m, tr.X, tr.h_prev, tr.nofire = nil, 0.0, nil, false

-- 帧回调（UpdateBehavior 前，与探针 EMINFO 同一时刻），对每个活着的结果，不论是否在蓄力，先于求值：
local C  = core_of(tr.idx)            -- pcall；同一帧按 idx 缓存；读不到返回 nil
local h  = clock_hs(tr)               -- 同一条条目相邻两帧 hs 的读数（条目消失就换一条；都没有就这帧不累加）
local ok = finite(C) and C >= 0.5 and C <= 2.0
if tr.m == nil then                   -- 登记后第一个帧回调 = 离线验证的采样点
  if ok then tr.m = math.max(1.0, C) else tr.nofire = true; stats.speedfail = stats.speedfail + 1 end
else
  if h and tr.h_prev then tr.X = tr.X + (tr.h_prev - h) * (tr.m - 1.0) end   -- 上一帧到这一帧怪物多走的名义帧
  if ok then tr.m = math.max(1.0, C) else stats.speedhold = stats.speedhold + 1 end
end
tr.h_prev = h

-- consider（蓄力中）：
--   否决：照旧按原始 e.hs ≤ 90、e.he ≥ 0、长窗口 / 抓取；另计长窗口条目 (e.hs − X)/m ≤ 90 < e.hs 的次数（vetoq）
--   候选：not tr.nofire、tr.m 已有、DANGER、非效果 / 弹体、副本闸门同 v1.5.1、0 ≤ e.he − e.hs ≤ 60，
--         Q = (e.hs − (tr.X − X0[e])) / tr.m，22 ≤ Q ≤ L；ev.best 取 Q 最小的那条
```

### 5.3 运行时开销

- **登记时**：钩子里不新增调用。
- **每帧**：每只有活着的结果的怪 3 次调用（找怪、取角色、读 CoreState）；每个活着的结果多读一条条目的 hs（约 4 次调用）。现有数据里同时被跟踪的结果很少：APCal 的 PERF 快照中位 0、p90 1、最多 2（审查复算）。
- **不需要**：读 calcMotionSpeedTotal、跨帧持有怪物对象、os.clock 时钟。
- **开销**：现行放刀模块占帧时间中位 0.22~0.25%（4 段 STAT，复算），即使翻倍也远低于 5% 的门槛；B 阶段实测。
- **区间变窄**：[22, 25] 只有 3 帧（0.05 s），帧率 ≥ 20 fps 时至少有一帧落在里面。回放里「不触发」的比例没有变多：复算样本二 10/50 对 11/50，（C）主集 19 对 18。

### 5.4 读不到时怎么办（fail-safe）

- **单个结果读不到**：首帧读不到，这个结果不放刀、照样参与否决，计 `speedfail`；中途读不到，沿用上一帧的 m，计 `speedhold`。不回退到 v1.5.1 的 E0@30：那个口径在现有数据上放早约 26%（复算 66/90 落窗），是已知会失败的口径。
- **连续 5 个新结果首帧都读不到**：标黄（可选模块 `speed`），菜单状态行写「速度读不到，已停止自动放刀」。不停用读取，下一次读到就恢复。
- **现有数据里**：C 读取 100% 成功（2805 条 EMINFO），所以这条只影响退路是否安全。
- **联机副本**：照旧不放刀。副本的 Replica / WaitPacket 分量不在本规则的验证范围内。

### 5.5 记录（离线验收和监控要用）

- **FIRE** 在原字段后追加：
  - `C1`：首帧 C；
  - `Cf`：放刀时的 C；
  - `nchg`：m 变过几次；
  - `X`、`Q0`：放刀时的累加量和触发量；
  - `Qe1`：影子 E1，`hs − A·(1 − 1/m1)`；
  - `mode`：E5c。
- **HDR** 追加：`rule=E5c`、`L`。
- **STAT** 追加：`speedfail`、`speedhold`、`vetoq`。
- **RES** 可选追加 `hit`：信用窗口内主角是否进了受击动作。这样不开 APCal 时也能粗分放早，供 C 阶段监控用。
- 分析脚本要按版本识别 v1.6 的口径（L、Q、E5c），影子回放也改用 Q。属于实现阶段的工作。

### 5.6 配置迁移

v1.6 起 `parry_lead` 的含义变成「真实剩余帧」，存配置时写 `cfg_ver = 3`。读到 `cfg_ver < 3` 的配置时，`parry_lead` 一律改成用户确认的默认值（25 或 28），并写一行 DBG `cfg_upgrade`（口径同 V15.md 第 9 节）。滑块范围改为 23~45，说明文字写成「真实剩余帧，已按怪物速度修正」。

### 5.7 前置：引用记账修复（B 阶段的前提）

`docs/NOTES.md`「跨帧持有与 REF 的引用记账」：两个脚本同时持有同一个结果对象时，谁先 `release()` 就扣掉了唯一的游戏侧引用，另一个就拿着悬空指针。

- 11:00:51.259，APCal 关闭 EP id=126（end=fin，会 release）；
- 11:00:51.274，`[AutoParryGS] ERR mod=frame level=red msg=caught_(...)_exception`；

## 6. 新探针（A 阶段）：要先跑

上一版说「参数不需要新数据」。审查后这句话撤回：C 的读取时刻、E5 对 E1、其他速度分量、新怪的左尾和攻击几何，都需要新数据才能回答。好在探针基本是现成的，而且只记录、不放刀，不会多挨打。

### 6.1 用现成的 ATP + APCal，要补的东西

仓库里的 `probes/AttackTimingProbe.lua`（ATP，未跟踪文件）已经有：
- `INIT`：initData 那一刻的怪物快照，就是钩子时刻的 C；
- `EMF`：每帧帧开头一条，含速度、动作层帧号与速度、DeltaTime；
- `EMSPD`：`_MotionSpeed` 的 12 个分量，有变化就记；
- `EMACT`：动作切换。

ATP 不跨帧持有游戏对象，可以和 APCal 同跑。APCal 提供 SER / ATK / CT / MSG / ENT。

还要补：
1. **APCal 的 ATK 钩子**：
   - 第一句按 owner 过滤，只放行当前有被跟踪结果的怪；
   - 限频守卫改成按钩子体耗时（ms/s）计算，只统计放行的调用；
   - 每个 (em, a5) 在 0.3 s 内只记第一次。

   原因：2b（44297.67）和 2c（68399.54）附近小怪多（em39、em40），`activateAttack` 每秒超过 3000 次。守卫按调用次数关掉钩子之后，整段都没有 ATK，2c 只有前 620 s 能用。
2. **离线配对**：ATK 用 a5 ∈ `CollidableIDList` 对到条目，再加怪物当前动作。`tools/atp_analyze.py` 的 C3 已有这个口径，并带零假设对照：a5 多是 0~9 的小整数，偶然命中可能很多，所以只有命中率明显高于「时间带平移」的对照时才用 cids，否则退回时间窗。逐只怪报告配对率，并列出没配上的招。
3. **离线分析要加**：
   - E5 对 E1；
   - 按物理激活去重后的「所有活着结果取最早」联合预测残差；
   - 后继结果的登记提前量；
   - 每只怪的 g 分布，以及按 r_raw + g 预测的 L=25/28 放早率；
   - 第 7.1 节的合并判据；
   - 钩子时刻（INIT 快照）与首帧 C 一致的比例，按招列出不一致的。
4. 其余保留：SER、MSG、ENT、EMINFO、CT、ACT、EMHIT、EMSTATE、PERF。

### 6.2 怎么跑

- 放刀模块关掉（`auto_parry = false`），这时没有双重持有的问题；ATP + APCal 开着。
- **在 A 之前，先由用户在 L=25 和 L=28 之间定好**。A 阶段不用来选 L，这样 A 通过后，同一批怪可以直接用于 B（第 7 节）。如果想看了 A 的左尾数据再选 L，A 的怪就变成设计数据，B 要另找 4 只。
- **选怪**：至少 4 种设计阶段没出现过的大型怪，即不是 Em0151 / 0152 / 0153 / 0156 / 0160，也不是训练机关 Em0165。必须包括：
  - 1 只历战个体，它的速度倍率从哪个分量进来还不知道；
  - 1 只怒时明显变快的怪；
  - 1 只多段长连招、长预告多的怪。
  尽量再覆盖体型很大或很小的怪。
- **每只 10~12 分钟**：站在攻击范围内，多数时间按住抵消蓄力或站着吃招（可以开锁血测试项）。至少打出一次发怒，尽量打到疲劳。目标是每只怪至少 60 个能配上 ATK 的单位：2a 7.1 分钟攒了 36~46 个，2c 前 620 s 攒了 58 个。

## 7. 预注册的验证与验收

原则：**规则和参数在进新数据之前定死（包括用户选的 L），新数据只用来判定通过或不通过**。新数据里任何一只怪如果被拿来改规则或改参数，它就变成设计数据，之后的验收必须换别的怪。

### 7.1 A 阶段：机制检验（只记录，≥ 4 只新怪）

**单位**：

**预注册的 E5 判定**：在存活期 C 变过的单位上，如果 E5 的 |r| 中位不大于 E1 的，保持 E5c；否则改用 E1（首帧读一次）。改了就算新迭代。

**只报告、不判**：
- 每只怪的左尾比例；g 分布；按 r_raw + g 预测的 L=25 / 28 放早率；
- 后继结果的登记提前量（< 0.45 s 的比例）；按物理激活去重的联合预测残差；
- C 的范围；各分量 ≠ 1 的比例和残差对 `A·(1 − 1/分量)/60` 的斜率；
- 钩子时刻与首帧 C 一致的比例；
- UNABLE_GUARD 条目；C < 1 子集；有没有 EMHIT（主角先砍中）两组的差别。

**结论怎么下**：
- 1~5 全过，且没有一只怪被标「系统性」→ 机制通过，进入 B 阶段，A 的怪可以直接用于 B。

- 只是个别招的左尾 → 规则不变，如实报告。要不要改 L 由用户决定；改了就是新迭代。
